# MiniRAG 企业化升级学习指南

## 目标

企业化升级的主要产出不只是代码，而是以下能力：

1. 从业务问题推导技术需求。
2. 比较多个可行方案并说明取舍。
3. 设计稳定的数据模型、接口和状态机。
4. 识别失败路径、一致性问题和安全边界。
5. 用测试、指标和故障演练证明实现有效。
6. 在理解设计后使用 AI 提高编码效率，而不是让 AI 代替设计过程。

## 标准训练循环

以后每个小任务严格按以下顺序推进。

### 1. 问题定义

先回答：

- 当前系统具体哪里不够？
- 这个问题在什么数据规模、并发量或业务场景下出现？
- 不解决会导致错误、泄露、性能浪费，还是运维困难？
- 本轮明确不解决什么？

产物：一段问题陈述和清晰范围。

### 2. 现状追踪

沿代码画出当前数据流，例如：

```text
上传文件 -> 文档目录 -> 解析 -> Chunk -> Embedding -> 索引 -> 检索 -> 生成
```

必须找出：

- 数据在哪里创建和保存。
- 哪些 ID 是稳定身份，哪些只是展示字段。
- 缓存何时命中和失效。
- 失败后系统处于什么状态。
- 哪些模块会受到本次修改影响。

产物：现状数据流、关键文件和风险点。

### 3. 方案比较

至少比较两个方案，不为了数量虚构无意义方案。比较维度包括：

- 正确性和一致性
- 实现复杂度
- 性能和成本
- 可维护性
- 可测试性
- 向后兼容需求
- 当前项目规模是否真的需要

产物：方案表和明确选择理由。

### 4. 编码前设计

编码前写清：

- 数据模型和唯一约束
- 输入、输出和错误接口
- 状态变化
- 正常路径与失败路径
- 幂等性和并发行为
- 缓存键与失效条件
- 最小测试清单

如果这些内容说不清楚，就不进入编码。

### 5. 小步实现

> 默认分工：AI 在用户确认的设计约束内编写实现与测试；用户负责选型拍板、逐行审查，并能脱稿复述数据流和失败路径。用户手写代码仅在核心难点且用户主动要求时进行。

一次只实现一个可测试能力，例如：

```text
先实现 chunk_text_hash()
再实现单个向量缓存读取
再实现批量缺失向量计算
最后接入索引构建
```

AI 可以：

- 给局部 API 示例
- 评审用户代码
- 解释报错
- 补充边界测试
- 执行验证命令

AI 不应直接跨过设计，完成整个阶段。

### 6. 验证与复盘

至少验证：

- 正常输入
- 重复操作
- 内容变化
- 空数据或损坏数据
- 中途失败
- 删除与恢复
- 缓存命中和失效
- 旧功能回归

完成后回答：

- 这次修改真正解决了什么？
- 指标或测试证据是什么？
- 还有什么边界没有解决？
- 如果规模扩大 100 倍，哪里会先失效？
- RAGFlow/MaxKB 为什么会采用更复杂的方案？

## 已完成阶段的补课方式

阶段 1 和阶段 2 已由 AI 较多地直接实现，需要逆向补课，而不是继续向前堆功能。

### 阶段 1：文档生命周期

需要做到：

- 能画出 `Document -> DocumentVersion -> Blob -> Chunk` 的关系。
- 能解释 `document_id / version_id / content_hash / chunk_id` 的区别。
- 能解释相同内容重复上传、内容更新、解析失败、逻辑删除和重新上传的状态变化。
- 能指出 SQLite、本地 Blob、软删除和当前索引重建方式的生产边界。
- 能独立修改一个行为并补测试，例如增加版本恢复或文档详情接口。

### 阶段 2：多格式解析

需要做到：

- 能解释为什么先统一转换为 Markdown，而不是每种格式维护一套 Chunk 流程。
- 能讲清 DOCX、HTML、PDF 各自保留和丢失了什么结构。
- 能解释文本 PDF 与扫描 PDF 的区别。
- 能指出表格、图片、页码、复杂版面和 OCR 的当前边界。
- 能独立增加一个解析边界测试或改进一个适配器。

## 下一训练任务：阶段 3.1

主题：Chunk 内容哈希与 Embedding 复用。

先不写完整增量索引。第一轮只回答：

1. 为什么文档更新后不能继续用 `chunk_id` 作为向量缓存键？
2. 为什么缓存键必须包含 Embedding 模型身份？
3. 相同文本出现在不同文档中，能否复用向量？复用会不会混淆权限和引用？
4. Chunk 文本 Hash 应该在规范化前还是规范化后计算？
5. 缓存文件损坏、维度不符或模型切换时应该怎么处理？
6. 用什么测试证明只修改一个章节时，其他章节没有再次调用 Embedding API？

完成回答和方案评审后，第一段代码只实现并测试：

```python
def embedding_cache_key(model: str, text: str) -> str:
    ...
```

不要在同一步接入完整索引重建。

## 面试训练要求

每个阶段最终准备三种表述：

1. 30 秒：问题、方案、结果。
2. 3 分钟：数据流、关键取舍、测试证据。
3. 深挖：失败路径、替代方案、规模边界和下一步设计。

面试中不把原型包装成完整生产系统。明确说明已完成能力、未完成能力以及继续演进的原因，比堆叠“企业级”术语更可信。
