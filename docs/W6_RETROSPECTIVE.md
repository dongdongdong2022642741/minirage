# W6 复盘：MiniRAG（从零手写 RAGFlow 式检索链路）

> 数字口径：检索评测与端到端评测均在**全量语料 31,826 篇**上产出
> （`python eval_retrieval.py` / `python eval_e2e.py`，任务 1 收官轮）。
> 测试 99 条全绿，重跑零 API（全部走缓存）。

## 一、项目回顾（What we built）

**一句话主线**：从零手写一条 RAGFlow 式检索问答链路——文档解析、2-gram 无词表分词、自研 BM25 + bge-m3 向量双路召回、RRF/加权融合、融合集内 rerank、DeepSeek 带引用生成，并在开源基准 NoMIRACL 中文 393 条 query 上闭环评测，5 周完成。

| 周次 | 交付物 | 核心代码文件 | 测试数（累计） |
|---|---|---|---|
| W1 | 文档解析：Document 对象 + 目录/空文件/编码容错 | docparser/ | 15 |
| W2 | 分块策略：固定长度 size+overlap + 标题栈父子分块 | chunking/ | 39 |
| W3 | 倒排索引 + 向量检索：自研 BM25 + bge-m3 + 向量缓存 | index/ | 58 |
| W4 | 混合融合 + rerank：RRF/加权统一接口 + 集内重排 | index/fusion.py、index/rerank.py | 86 |
| W5 | 评测闭环：393 条检索评测 + RAGAS 式端到端评测 | eval_retrieval.py、eval_e2e.py | 99 |

**链路图**：

```
文档 → 解析(容错) → 2-gram 分词 → ┌ BM25 倒排 ──┐
                                   ├ RRF/加权融合 ─ RRF 集内 rerank ─ DeepSeek 带引用生成 ─ 引用合法性校验
                                   └ bge-m3 向量 ─┘
```

## 二、最终成绩（数据说话）

### 检索评测：NoMIRACL zh 393 query（全量 31,826 篇 passage）

| 方法 | recall@5 | recall@10 | MRR@10 |
|---|---:|---:|---:|
| bm25 | 0.3597 | 0.5581 | 0.3572 |
| vector | **0.7785** | **0.9358** | **0.7684** |
| rrf | 0.6469 | 0.8835 | 0.6225 |
| weighted | 0.7209 | 0.9013 | 0.6681 |
| rrf+rerank | 0.7209 | 0.8835 | 0.6447 |

- 向量全面胜出 BM25（recall@10 +0.3777）；RRF 平均低于较优单路（输 66 / 平 319 / 赢 8），归因 RRF 排名平权，非候选空间不足
- rerank 把 recall@5 从 0.6469 提到 0.7209（+0.0740，88 个 query 受益），recall@10 不变——集合不变只修排序

### 端到端评测：15 query × 2 路（全量 + 喂料 top-10）

| 方法 | 能答率 | faithfulness 平均 | relevancy 平均 | 引用合法 |
|---|---:|---:|---:|---:|
| vector | 15/15 (100%) | 0.955 | 0.781 | 15/15 |
| rrf+rerank | 15/15 (100%) | 0.844 | 0.770 | 15/15 |

- 从 W5 中期的 9/15（60%）经三轮修复（喂料 top-10、低温度、拒答重试、提示词放权）到收官 15/15
- 覆盖失败病例 7273910/7832551 证实为语料覆盖问题，全量语料下痊愈（faith 双 1.0）；5304336 为语料真缺失（无"学名"直接表述），模型硬推付出 faith 代价
- 测试 99 条全绿；两个评测脚本缓存后重跑零 API，离线可复现

## 三、踩过的坑（现象 → 原因 → 判断 → 做法）

### 1. 中文分词——误判"中国的首都是北京"首 token，实际 2-gram 正确

- **现象**：排查该 query 的匹配过程时，直觉认为分词首 token 应为"中国"，怀疑 2-gram 产出"中国的"之类碎串、首 token 语义丢失。
- **原因**：用**词切分**的直觉去审视**字符 n-gram**——两者粒度完全不同，n-gram 不感知词边界，视觉上"不像分词"。
- **判断**：这不是 bug。2-gram 的数学性质是"query 内出现的任意词，其所有相邻两字子串必然在 gram 集合中"，召回不依赖分词质量；代价是噪音多、idx 大，换来零词表维护。
- **做法**：写测试锁定 gram 生成的确定性（长度恒为 2、覆盖 query 内每个字符），并以"该 query top-1 命中来自'中国'这个 gram"实证。

### 2. docid 类型——qrels 的 docid 形如 "131888#0"，bm25 里误用 int

- **现象**：BM25 检索结果与 qrels 标注对不上，recall 一度全 0。
- **原因**：BM25 索引内部把 doc_id 转成 int 存储（截断 `#0` 后缀），qrels 从 TSV 读出的却是原始字符串，两边"看起来是同一个文档、实际不是同一个键"。
- **判断**：doc_id 是跨语料/索引/评测的**全链路契约**，任何一层私自做类型转换都会制造"假 miss"，且错误藏得极深（不报错、只悄悄对不上）。
- **做法**：统一 str 契约——加载、索引、返回、评测一律保留原始 doc_id；补类型与往返一致性断言。

### 3. 融合不是免费午餐——6402503 融合把能答的搞成拒答

- **现象**：e2e 中 query 6402503#0，vector 单路能答，融合路（rrf+rerank）的 top-10 喂料丢了相关文档，LLM 答"资料不足"。
- **原因**：RRF 排名平权：BM25 给噪声高分、向量给相关文档高分，融合后排位被平均化，相关文档被挤出喂料窗口（检索评测同款现象：query 1719936#0 vector recall@5=1.000、bm25=0.000，rrf 掉到 0.400）。
- **判断**：融合在**平均指标**上赢，但**单 query 必然有输给单路的时刻**——这是方法的天性，不是 bug；用单条胜负评价融合=以偏概全。
- **做法**：e2e 双路同测（vector / rrf+rerank 并列输出），结论只从配对平均与分布下，禁止用单条胜负下结论。

### 4. rerank 救不回 recall——集合不变是天花板

- **现象**：rerank 前后 recall@10 完全相同（0.400 → 0.400），只有顺序变化。
- **原因**：rerank 只在融合产生的集合内重排；相关文档若已被融合丢出集合，rerank 无文档可救。
- **判断**：召回天花板由**集合**决定，排序优化救不了召回；把"rerank 能提升召回"的期待是错误的。
- **做法**：rerank 定位为"集合内提精"，召回提升的期望放在检索端（RAW_K、融合方式）；评测同时输出 recall@5/10 与 MRR@10，排序相关的指标单列，避免误判归因。

### 5. 缓存假数字——query 嵌入缓存按 hash 区分、e2e 缓存必须带版本

- **现象**：语料从 4,000 篇切到全量 31,826 篇后，检索结果全部变化；若 e2e 答案缓存仍按旧文件加载，就是"新检索 + 旧答案"的假数字（本项目的踩坑原型：e2e_cache_N4000.json 遗留）。
- **原因**：缓存 key 只编了语料规模（或什么都没编），没编**数据内容版本 + 生成配置版本**；命中即复用，但命中语义不等于"重跑结果不变"。
- **判断**：缓存命中的充分条件是"重跑产出逐字节一致"；无法保证时，缓存是 bug 发生器，不是优化。
- **做法**：query 嵌入缓存按 `N + 查询内容 hash` 命名；e2e 缓存文件名带 `N` 与 `topK`，文件内嵌提示词/温度/重试配置指纹，加载时校验，不一致直接报错（fail loud），绝不静默复用。

### 6. 评测红线——3 条 demo query 上调参 = 过拟合

- **现象**：W4 融合在 demo 3 条 query 上"1 条 FAIL、1 条 PASS、1 条平手"，好时坏时无从解释，存在强烈的"调 RRF_K/alpha 调好它"的诱惑。
- **原因**：3 条样本不足以区分方法差异与采样噪声；任何在这 3 条上"调好"的参数都是对这 3 条的过拟合。
- **判断**：参数决策只能发生在**独立且足够大**的评估集上（393 条全量）；demo 只配做方向性验证。
- **做法**：立红线——所有参数保持 W4 默认，等 W5 在 393 条全量上一次性出表；报告显式声明"未在 393 条上调参"，堵死事后诸葛。

## 四、对照商业实现（MaxKB）

> 对比基于 MaxKB 公开产品认知（文档/产品页），未对其源码实测；差异要点为我方视角。

| 环节 | MiniRAG | MaxKB | 差异要点 |
|---|---|---|---|
| 关键词检索 | 自研 BM25（倒排 + 2-gram + IDF） | Elasticsearch 系 BM25 / 内置关键词 | 自研全链路可控，参数可解释 |
| 分词 | 全自动 2-gram，零词表维护 | 内置分词 + 手动维护 Termbase 术语词表 | 我方全自动兜底；对方术语词表更精准但靠人 |
| 向量检索 | bge-m3 + 自研 numpy 检索（缓存化） | pgvector / ES / Milvus / Weaviate 可插拔 | 我方小规模自研可迁移；对方工程化成熟 |
| 融合 | Python 显式 RRF / 加权统一接口 | SQL 内权重 blend 一次算完 | 我方显式可解释、便于拆解归因（坑 3/4 就是这么查出来的） |
| rerank | bge-m3 交叉打分，融合集内重排 | 支持接入 rerank 模型 | 思路一致 |
| 生成 | DeepSeek + 带引用提示词 + 拒答重试 + 引用合法性校验 | LLM 生成 + 引用来源展示 | 我方多了"资料不足"重试与引用合法性指标 |
| 评测 | NoMIRACL 393 条 recall/MRR + 自研 RAGAS 式 e2e | 内置基础命中率评测 | 我方用开源基准 + 双指标，可复现可对比 |

**一句话对照**：商业产品赢在工程化（可插拔、托管、规模），但链路是"配置出来的"；本项目赢在**每一步都亲手实现且可归因**——坑 3/4 的结论如果不是显式 RRF 和显式评测，根本查不出来。

## 五、重来一次会改什么

1. **向量库一开始就全量建**。当时为控成本用 1,000→4,000 篇切片，把"语料覆盖不足"和"检索方法不行"混成了一个问题：idf 偏斜、5304336 类"资料不足"都可能被误判为方法缺陷，还间接制造了 N4000 缓存假数字坑（坑 5）。正确的做法是先花半天把 31,826 篇全量建库（本项目实测构建约 2 分钟量级），让评测永远只回答"方法行不行"。
2. **relevancy 用 LLM-as-judge，而不是 embedding 余弦**。0.45 余弦阈值在收官轮完全退化：rel 通过率两路 100%、最低分 0.68，无区分度，等于没测。LLM-as-judge（"答案是否直接回答提问"）虽然花钱，但给出的是二值判断而非相似度残差。
3. **e2e 样本从 15 条扩到 50**。15 条下平均指标被单条采样波动牵着走（5304336 一条就从 0.4 摆到 1.0），配对差 0.01~0.08 的结论都不可信；50 条才能区分"方法差"与"运气差"。
